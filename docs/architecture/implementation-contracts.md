# Implementation contracts — Phase 1, Step 2

Status: documentation baseline, 2026-11-21. No application code, dependencies, production changes or deployment. This document is normative for Step 2; the other seven documents provide context. Numerical limits are provisional pilot defaults. IDs and dates in examples are fictitious. Examples are wire documents, not implementations.

## Final MVP architecture

One feature-based TypeScript Node.js/Express/Mongoose backend, separate API, worker and scheduler processes, one MongoDB replica set and private Redis/BullMQ. React JavaScript/Vite on Vercel talks to the VM HTTPS API and Socket.IO. Resend sends minimal incident emails. An external watchdog observes the platform from another failure domain. No Kubernetes, tenant framework, microservices, distributed locks service or general workflow engine.

The API commits bounded sanitized inbox receipts; workers claim MongoDB work after BullMQ wake-ups. MongoDB owns business state and retries. Nine fixed queue job identities replace per-record jobs and a custom Redis admission-permit protocol. Initial maximum ingest dispatch rate is two batches per five seconds: at full 100-event batches, 40 events/second before processing cost. Partial batches lower effective throughput. This is a pilot ceiling, not a capacity claim; reject overload and measure before rollout. Independent check lanes prevent a telemetry backlog from consuming probe concurrency, though CPU and database are shared.

| Classification | Included |
| --- | --- |
| Mandatory MVP | Single admin; projects/environments/keys; bounded SDK; durable ingest; raw reads; approximate minute metrics; safe error groups; independent health checks; rules/incidents; one email recipient; minimal dashboard and socket invalidations |
| Production safety, cannot defer for rollout | Transactional quota/deduplication/outbox; fencing; finite storage/retries; HTTPS and SSRF controls; revocable sessions; secrets exclusion; dependency timeouts; backup/restore; external watchdog; drop/staleness signals and capacity evidence |
| Later | Exact-percentile query service, hourly/year-long aggregates, statistical sketches, configurable sampling, raw-edge blending, reminder emails, multiple recipients/admins/RBAC, stack symbols, private-IP probes, horizontal API scaling |

### Ingestion alternatives and decision

| Concern | Direct BullMQ intake | MongoDB inbox + BullMQ wake-up |
| --- | --- | --- |
| Acceptance | 202 after Redis add; command ambiguity resolved by retry ID | 202 after journaled majority MongoDB transaction; ambiguous commit resolved by batch ID |
| Durability | Redis persistence policy determines loss; AOF every second can lose acknowledged writes | Accepted payload survives Redis loss while MongoDB survives and finite expiry has not elapsed |
| Recovery | Lost Redis payloads cannot be recovered without sender replay/spool | Indexed MongoDB pending/expired leases are rediscovered; Redis is disposable execution signaling |
| Complexity | Fewer writes; still needs quota, dedupe, bounded jobs, outage policy | More transaction/index/retention operations; shared durable work pattern for inbox/checks/outbox |
| Storage | Payload in Redis, plus MongoDB after processing; Redis RAM is expensive | Payload temporarily in MongoDB plus raw data; Redis contains nine small wake jobs |
| Outages | Redis outage rejects intake even when MongoDB works | Redis outage buffers finite intake; MongoDB outage rejects acceptance and auth |

**Decision:** initial durable inbox. Existing safety expectations include recovery of accepted work after Redis loss; direct BullMQ would weaken that guarantee. Accept the replica-set requirement and extra writes. A single-node replica set permits transactions but has no host/disk redundancy. [MongoDB transaction prerequisites](https://www.mongodb.com/docs/manual/core/transactions-production-consideration/).

## Shared HTTP and validation contracts

Base path `/api/v1`; JSON UTF-8, UTC RFC3339 millisecond dates, half-open intervals `[from,to)`, ObjectId strings for persisted entities, UUIDv4 for batch/event/boot IDs. Omitted optional fields are absent, not arbitrary null. Counters/durations are nonnegative safe integers; reject overflow, NaN, Infinity and coercion. All user-provided strings are length-bounded, all objects strict, arrays bounded. Unknown fields fail validation. Reject Mongo operators and dotted field names; never pass query/body objects directly to a model. Response DTOs omit digests, cookies, internal exceptions and arbitrary model fields.

Success: `{ "data": <document-or-array>, "meta": { "requestId": "...", "asOf": "2026-11-21T06:00:00.000Z" } }`. List meta additionally has `nextCursor` (opaque string or null). Failure: `{ "error": { "code": "INBOX_FULL", "message": "Telemetry intake is temporarily full.", "retryable": true }, "requestId": "..." }`. Validation issues may contain at most 20 static field paths and codes, never submitted values. No stack or provider/database text in responses. All errors and success responses carrying auth/secrets use `Cache-Control: no-store`.

Status mapping: 400 malformed JSON/query/cursor; 401 absent/invalid credential; 403 scope/origin/CSRF denial; 404 missing or wrong-parent entity; 409 revision/hash/state conflict; 410 expired receipt/replay horizon; 413 encoded body too large; 415 compressed/non-JSON body; 422 valid JSON violating DTO/version/time rules; 429 bounded admission/rate limit; 503 unavailable dependency; 500 unexpected defect with safe request ID. Retryable 429/503 include integer `Retry-After` 1–60 seconds. The server returns a generated request ID rather than logging arbitrary supplied correlation strings.

Zod boundaries: startup process-specific environment; HTTP path/query/body separately; SDK construction and pre-serialization event; server intake again; persisted job envelope; monitor/rule configuration; safe provider response; outbound socket envelope. Mongoose schemas enforce persistence invariants and indexes, not authorization. Business services validate ownership, current revision, timestamp policy and state transitions after Zod. JSON parser limits apply before Zod. Database validators/index migrations are explicit; no production auto-index or destructive sync.

Non-create mutations use expected `revision`; stale revision yields 409. Creates return 201 except ingestion/replay 202; other successes return 200, including logout. Retried admin creates may return 409 for an existing natural key and then read it; no implicit generic idempotency framework. Server computes project/environment binding from parent and database references. Disabling a project/environment disables its monitors/rules, revokes keys and resolves incidents with administrative reason in a bounded maintenance workflow; new work is denied immediately using enabled flags. Hard deletion is deferred.

DTO details: slug/name/environment names use reviewed ASCII identifiers (slug 1–64, display name 1–100, environment 1–32); immutable slug/name after create. Route templates ≤160 characters, ≤200 per environment; configured parameter placeholders only, no actual URLs/query/fragment. `routeKey` is an immutable server-assigned route registry ID; SDK sends `routeTemplate`, server resolves it. Reserved `__unmatched__` and `__other__` do not consume the registry ceiling.

Monitor DTO: `name` ≤80, `url` ≤512, `intervalSeconds` integer 30–3600 (default 60), `expectedStatusMin/Max` integers 200–299 (default 200/299), `enabled` boolean, optional `maintenanceUntil` ≤24h ahead. Exact host/path must already be operator-approved in destination policy; admin cannot self-authorize a forbidden network through this API. Rule DTO: kind `availability|error_rate|p95`, scoped monitor for availability or `project|route` normal completed metric population; threshold/recovery threshold, `minimumSamples` 1–100000 (default 100), `windowMinutes` 1–15 (default 5), `breachCount`/`recoveryCount` 1–10 (defaults 2/2; availability 3/2), `cooldownSeconds` fixed 900, enabled. Ratio thresholds are 0–1; recovery < breach. p95 thresholds are integer microseconds, recovery < breach. Availability streaks are per scheduled slot, never per HTTP retry. No arbitrary rule expression language.

## SDK telemetry contract

Envelope example (placeholder key never appears in the body):

```json
{
  "schemaVersion": 1,
  "batchId": "55555555-5555-4555-8555-555555555555",
  "projectId": "000000000000000000000001",
  "environmentId": "000000000000000000000002",
  "bootId": "66666666-6666-4666-8666-666666666666",
  "release": "release-2026-11-21",
  "events": [
    {
      "eventId": "77777777-7777-4777-8777-777777777777",
      "occurredAt": "2026-11-21T05:59:59.000Z",
      "method": "GET",
      "routeTemplate": "/api/orders/:orderId",
      "outcome": "completed",
      "statusCode": 200,
      "durationUs": 42100,
      "stream": false,
      "sampleProbability": 1
    }
  ]
}
```

Required envelope fields: schemaVersion exactly 1, UUIDv4 batchId/bootId, scope ObjectIds, events array 0–100. Optional release is a pre-approved label ≤64 chars. Optional heartbeat below; at least one event or heartbeat required. One boot per envelope; project/environment must match the key. Method enum `GET,POST,PUT,PATCH,DELETE,HEAD,OPTIONS,CONNECT,TRACE,OTHER`. Event fields shown are required except `statusCode`, which is required integer 100–599 for completed and absent for aborted. Duration integer 0–86,400,000,000 µs; occurredAt is completion time, not start; stream boolean separates distributions. MVP probability must equal 1; a future schema/config change is required to enable sampling.

Optional event `error` is `{type,code?}`: type enum `UnhandledError|Timeout|ApplicationError|DependencyError|UnknownError`; code from a configured allowlist ≤64 chars. One error occurrence per requestEventId; error occurrence identity equals request event ID in its separate collection. No independent error-only events or frames in MVP. HTTP 5xx without error metadata still contributes to server error metrics, not fabricated exception groups. Validation forbids bodies, query strings, raw paths, headers, customer IDs/IPs, free-form messages and stacks.

Optional heartbeat: `{sequence,observedCompleted,observedAborted,selected,acceptedByApi,dropped:{overflow,oversize,retryExhausted,permanentReject,shutdown},retryAttempts}`. All counters cumulative safe integers since boot, sequence ≥1; heartbeat timestamp is server receipt time. SDK selects once per eligible request; retries never increment selected. acceptedByApi counts events in acknowledged batches once, not duplicates; shutdown loss may be unreportable. A newer sequence must not decrease counters. Older sequence is ignored; same sequence/different content is a conflict. Missing boot heartbeats after 90 seconds mark coverage unknown, never target down. Cap active boot IDs to 20/environment and persisted states to 200/environment; admission of a new boot fails 429 if full until explicit expiry. Restart gaps and final unreported losses cannot be reconstructed exactly.

SDK bounds: 1,000 events/2 MiB including in-flight and retries; 8 KiB/event; 100 events/256 KiB envelope; five-second jittered flush; one in-flight send; 3-second total HTTP deadline; five total attempts within ten-minute age; 30-second heartbeat; no disk spool. Immutable retries preserve batch ID/body/event IDs. Drop oldest non-in-flight event on overflow, otherwise new event; record reason. No request-path awaited I/O, stream reads, global exception handlers or response modifications. Completion/abort listener records once. Optional error observer calls next(error) exactly once. Explicit shutdown flush ≤2s; crashes lose memory and final counters. On 401 stop sends until configuration changes; on 403/409/410/422 count permanent rejection; on 408/429/5xx/network failure bounded retry with jitter and Retry-After ≤60s. Errors in telemetry capture are contained.

## Ingestion acceptance and idempotency

`Authorization: Bearer <project-scoped-key>` only; no URL/cookie keys. Proxy limits: JSON body ≤262144 bytes, no content encoding, header bytes ≤16 KiB, body/header deadline 5s, durable operation deadline 2s and response deadline 8s. Bound simultaneous body parsers to 8/API and durable intake transactions to 4/API. SDK's 3-second deadline may expire after commit: retry resolves it. Key lookup/auth before deep event validation; no positive auth cache.

Initial single-API fixed-window rate caps per ten seconds: IP 200 HTTP requests, key 50 new batches/1000 new events, environment 100 new batches/2000 new events; global 200 new batches/4000 new events. Count attempted requests for IP/abuse caps, including duplicates; matching receipt retries bypass new-event quotas but not abuse/connection caps. Rate windows are atomic local counters, bounded to configured keys and at most 1024 IP buckets; reject new IP buckets when full. Known proxy sources only. In-memory reset on restart is acceptable because durable global/project quotas still bound accepted backlog. Multiple API replicas are unsupported until shared rate limits replace these counters. These caps protect ingestion; they do not assert processing can sustain the ceiling.

Hard pending inbox caps: global 2000 receipts/128 MiB canonical JSON payload; environment 400/24 MiB; project 800/48 MiB; all checks must pass. Reject 429 with `INBOX_FULL` before accepting more. Finite terminal receipt budget 20,000 compact records globally; if exhausted, reject new intake until retention cleanup frees room; never evict receipts inside dedupe horizon. Serialized quota document reservations and receipt insertion share one transaction. Budget rows contain pendingCount/pendingBytes plus totalReceiptCount and configured limits; conditional increments, never count-then-insert. Payload budgets exclude BSON/index overhead, so disk high-water policy is an additional mandatory guard.

Authenticate, validate shape and sanitized canonical representation, look up unique `(project,environment,batchId)`. Canonical hash = SHA-256 over the entire allowlisted envelope using sorted object keys, preserved array order, UTF-8 JSON and normalized UTC date representation; no transport headers. Equal existing hash returns existing receipt even if events are now older than ten minutes or current quota is full; conflicting hash yields 409. Enabled/revoked credentials still apply to retries. Only new batches undergo event age [-10m,+2m] and new-intake quota checks. Duplicate receipt query and insert races resolve through unique index, then re-read. Commit uses snapshot read concern, majority+journal write concern and bounded whole-transaction retry; unknown commit outcome resolves by ID, otherwise 503 and same-ID SDK retry.

Example 202 data: `{receiptId:"...",batchId:"...",state:"pending",acceptedEvents:1,duplicate:false,expiresAt:"2026-11-22T06:00:00.000Z"}`. Duplicate processed receipts also return 202 with `state:"processed",duplicate:true`; expired/failed loss receipts return 410 with a safe loss code. 202 means durable finite acceptance, not completed analytics or permanent preservation. No partial acceptance of malformed batches.

Per-event uniqueness additionally prevents replay in another batch. Store event contentHash over normalized event plus project/environment/boot/release, excluding batch and receive times. Same ID/equal hash skips all effects; same ID/different hash aborts that receipt and marks failed with `EVENT_ID_CONFLICT`, exposing lost events rather than silently overwriting. Receipt retention is not the sole event dedupe guard.

## Queue and recovery contract

Wake job envelope: `{version:1,kind:"ingest|probe|aggregate|evaluate|notify",lane:0}` with kind-specific allowed lane numbers. IDs/queues are the nine identities in [data flow](data-flow.md). Queue producers reject any other ID or payload; no repeat jobs, flow children, per-event job IDs or full telemetry. `attempts=1`, immediate removal on completion/failure, bounded stalled recovery on the pinned release. Ingest/probe/notify workers process at most one durable item per wake job and return no payload. Aggregate wakes process at most 20 windows and evaluation wakes at most 60 due rule scopes, each with a ten-second total wake deadline and one bounded transaction per item. The maintenance consumer alternates ready kinds so neither starves; unfinished pages wait for the next wake. Yield between items to preserve lock renewal and probe deadlines. Queue failure logs safe codes; durable record owns diagnostic evidence.

1. Scheduler runs a nonoverlapping five-second monotonic wake loop with bounded connection timeouts; add each known lane ID once per tick. Existing IDs suppress redundant wake jobs. Catch failures and try on next tick, without offline producer queues or recursive add. Adding same ID after removal is intentional. This uses documented [BullMQ ID lifetime](https://docs.bullmq.io/guide/jobs/job-ids), not permanent deduplication.
2. For each item within its bounded page, a wake consumer atomically claims one due pending item or expired lease, sorted oldest first within a round-robin environment cursor for ingestion. MongoDB CAS sets owner UUID, leaseUntil=now+30s and increments fence. No lease is acquired before the worker runs. On Redis loss a previously running worker may continue; only database fence permits its effects.
3. Each durable operation must finish within 10s, probe HTTP within 5s, provider send within 5s. Commit matches owner/fence and leaseUntil > now; conflict or lease expiry aborts all database effects. No automatic long lease extension in MVP. Reclaim increments fence; old workers cannot write current state. External probe/email side effects cannot be undone; their separate identity rules still apply.
4. Dependency outage detected before work does not consume an attempt. Pause that feature for 30s and release/retry safely if MongoDB is available; otherwise lease expires. Persist attempted failures when possible. Eligible transient business failures use at most five attempts with full-jitter ceilings 5s,30s,120s,600s between attempts. Attempt/fence claim and result must reconcile after a crash; a claimed operation counts as an attempt. Reclaim after ambiguous crash cannot exceed the recorded budget. Poison versions/validation fail immediately. Notification retry horizon is stricter below.
5. Crash after business commit but before BullMQ completion simply wakes again and claims other pending work. Crash before commit leaves uncommitted transaction invisible; reclaim after lease. A removed job needs no repair: next wake tick recreates it. Redis flush/replacement creates all nine wake IDs; MongoDB remains authoritative. Scheduler outage pauses new checks/wakes and becomes stale; no browser action is a recovery mechanism.
6. Pending receipts older than receive+24h explicitly expire in maintenance, with lost-event counters and budget release. Terminal failure after five attempts releases pending capacity and strips payload, except one operator replay may retain payload/reservation until the original 24h deadline; use `failed_replayable` to make that reservation visible. Manual replay is allowed once, with five further attempts, only before original deadline. Never revive an expired receipt or extend dedupe/loss horizons. Quarantine is compact reason/count metadata, not a second unlimited payload store.

Business transaction boundaries: (a) receipt + quota acceptance; (b) new raw/error inserts + group counters + dirty-window generations + heartbeat deltas + receipt processed + quota release; (c) due monitor advance + unique check run; (d) check final result + monitor in-flight clearance; (e) aggregate snapshot read + generation-CAS replacement; (f) alert state + incident + timeline + notification outbox; (g) refresh rotation/revocation and audit. Every mutation of durable work verifies its fence in that same transaction. Out-of-process pub/sub is after commit and best effort. No transaction spans external HTTP/email or Redis.

Maintenance selects a bounded page of 100, deadlines ≤10s; it expires pending work, strips terminal payload, removes due compact receipts while decrementing totalReceiptCount transactionally, records abandoned intervals and reconciles quotas. Scheduler owns lease-recovery/expiry work even during Redis outage; business processing still waits for Redis. Reconciliation of suspected counter drift pauses new intake while a bounded consistent recount occurs; no optimistic quota reset. Physical storage pressure can stop intake earlier than logical quotas.

Inbox states: pending → processing → processed; processing → pending on retry; processing → failed_replayable or failed; pending/failed_replayable → expired at deadline; failed_replayable → pending once on manual replay. Only pending/processing/failed_replayable reserve pending bytes/count. Terminal compact receipts survive 48h after terminal; TTL cleanup must be explicit for counted receipts (no TTL index on ingestion_receipts), so budget release and dedupe-record removal are atomic. They have `deleteAfter` instead of expiresAt. Event physical dedupe retention is ≥72h from original receipt; even the latest allowed replay cannot create duplicate counts after TTL. Visible raw queries still stop at 48h. A malicious reuse after all dedupe horizons is constrained by the ten-minute admission age; claims of dedupe are limited to retained identifiers, not forever.

Index refinements to the database table: metric_windows uniqueness includes `population` in addition to scope/granularity/start; aggregation_tasks windowKey includes population and has `(dirty,nextAttemptAt,leaseUntil)` and `(deleteAfter)`; counted task cleanup replaces its TTL index; ingestion `(state,nextAttemptAt,leaseUntil)` and `(state,originalDeadline)` plus `(deleteAfter)` for terminal cleanup; check_runs/outbox `(state,nextAttemptAt,leaseUntil)`; request route filter index includes method and occurredAt descending; metric rule reads use full scope+population+windowStart. Use partial indexes only with supported predicates; active incident uniqueness is `(ruleId,scopeKey)` where `isActive:true`. Error/event unique keys are `(projectId,environmentId,eventId)`. TTL indexes are separate single-field expiresAt/zero seconds; never TTL active incidents or pending work. [TTL deletion is asynchronous](https://www.mongodb.com/docs/manual/core/index-ttl/); service cutoffs are authoritative.

Historical operations: 6 projects, 3 environments/project, 30 monitors, 60 rules total, 2 active keys/deploymentGroup, 10 deployment groups/environment; changing these requires capacity review. Raw visible retention 48h (physical dedupe ≥72h), errors/checks/minute metrics 7d, error groups 30d inactivity, resolved incidents/timeline/audit 90d, terminal notifications 30d, sessions ≤30d. All provisional. A retained work cap stops new work rather than evicting dedupe evidence; terminal failures retain safe reason metadata until cleanup. Pending check runs capped at one per monitor; incident opening + outbox admission cannot silently discard a transition. Outbox global cap 1000 outstanding records: if full, commit incident with explicit `notificationSuppressed=capacity` and platform alarm; no fictitious delivery. Quality/loss intervals capped at 1000/environment, adjacent intervals coalesced conservatively to unknown ranges, retention 7d. Aggregation task cap is 50,000 globally (including completed retained tasks); reserve new-task capacity transactionally with event processing. If full, leave the receipt pending with AGGREGATION_CAPACITY rather than omit dirty markers; expiration records incomplete intervals. Trim eligible completed tasks explicitly with counter release; no task TTL may bypass counted cleanup. Cap unresolved incidents to configured rule scopes; no dynamic route fan-out rules in MVP.

## Analytics contract

`requestCount` is exact deduplicated received **completed** events in the chosen population and interval, including 4xx/5xx. Abort counts are separate, no invented 499. `serverErrorRate=5xx/requestCount`; zero denominator returns null, not zero. Client errors are separate. Error occurrences never add to request counts. `RPS=count/actual interval seconds`, `RPM=count*60/actual interval seconds`; these are completion rates, not instantaneous arrival rates. Return interval bounds and `coverage=complete|partial|unknown`; gaps do not shrink the denominator to make throughput look better. Mean latency is `sumDurationUs/count`, exact arithmetic over received data, weighted across bins. Safe-integer sum guard required; split computation or fail visibly on overflow.

MVP p50/p95/p99 use the 25-bin latency-v1 histogram in database-design. Counts and sums are exact for deduplicated data; percentile estimates are approximate with lower/upper bounds and sampleCount. Example: a duration 42100µs falls in `(32000,64000]`; one-event p95 has estimate 48000µs, bounds 32000/64000, approximate=true. Empty percentile/mean is null. A future exact query sorts at most 50,000 retained durations and uses nearest rank; it is explicitly excluded from MVP APIs. No t-digest/HDR/sketch service and no averaging p95s.

Ingestion marks project and route/method minute tasks dirty in the same transaction for each new event. Each task's requestedGeneration increments once per affected receipt; rebuild reads raw events in a snapshot, computes one whole window, replaces metric_windows and sets appliedGeneration only if requestedGeneration remains the captured value and fence holds. Concurrent arrivals force another rebuild. Max 100,000 raw records/window, database deadline 5s; above budget mark aggregate unavailable/over_capacity and alert, never silently truncate. At most 20 aggregate tasks per wake tick and ten seconds total; lag is visible. No hourly parents in MVP. No minute records for empty unknown scopes; a zero is emitted only when source quality supports zero observations.

Provisional charts may appear immediately. Historical eligibility requires minute end ≤now−12m, no overlapping nonterminal receipt (min/max event-time check), current generation, no known lost intervals and adequate heartbeat coverage. `completeThrough` advances monotonically only through eligible contiguous windows per scope; remains null when coverage cannot be established. It denotes received-pipeline completeness, never proof all production traffic was instrumented. Store late corrections with updated revision/asOf. Missing source inventory or heartbeat makes coverage unknown; known SDK drops mark incomplete. Delayed corrections do not retroactively page historical windows. Finalized high-error/p95 rules evaluate the latest eligible window once, skip stale (>15m beyond the normal watermark) evidence, and record insufficient_data otherwise. Rollup responses return actual aligned bounds, histogram method/version, sampleCount, observed/dropped counts, quality flags, asOf and completeThrough. Source drop counts derived from heartbeat deltas are approximate in event-time placement; present in receipt-time quality intervals without double-counting across routes.

## Health and incident contract

Scheduler MongoDB loop every second, independent of browser/API/SDK. Atomically advance nextDueAt and create unique `(monitorId,scheduledFor)` run in one transaction. Stable per-monitor jitter, no overlapping run. After downtime record a compact missed interval and create only current slot. A run starting ≥one interval late becomes missed, not failed. Superseded config/policy jobs become cancelled and never probe old destinations. DB failure prevents scheduling; Redis failure leaves at most one pending run/monitor, then missed slots are summarized. Fixed probe wake lanes cap concurrent network probes to four.

HTTPS GET only, port 443, no query/credentials/headers/redirects, approved hostname/path registry. Re-resolve all A/AAAA answers before each connection, reject any non-global/forbidden address, pin approved IP with original SNI/Host and certificate verification; no unchecked second resolution, proxy inheritance or cross-policy pooled socket reuse. Block internal/metadata networks at egress in probe transport context while allowing explicit DB infrastructure access separately. Total DNS/connect/TLS/read/response deadline 5s; response ≤16KiB then discard. Timeout is target transport failure only if worker/connection infrastructure was operating reliably; worker crash/no result yields unknown, never fabricated timeout. TLS/HTTP/transport failures describe reachability from this VM, not universal global downtime.

Persist one terminal result per scheduled slot: healthy, http_failure, transport_failure, blocked, infrastructure_failure, missed or cancelled. Only fresh healthy/http_failure/transport_failure affect availability streaks. Unknown/missed/blocked breaks pending consecutive streaks and blocks recovery; existing incident stays active with stale evidence. No retry of an already terminal slot; a crash may repeat external GET but CAS permits one observation. Three consecutive target failures opens, two consecutive successes resolves; acknowledgement stays active. Expected status and rule thresholds are provisional tuning defaults.

Alert evaluations CAS alert_state evaluatedThrough and rule version. Slot/window identity is unique; out-of-order/replayed results cannot advance streaks twice. Incident unique active index prevents parallel opens. Lifecycle: breach streak (state only) → open → acknowledged → resolved; subsequent breach creates a new incident. Unknown does not open/resolve target incidents. Maintenance continues observations but suppresses new target incidents/emails and pauses existing evidence; exiting requires fresh streaks. Disable/config change resolves active incident with administrative reason and no false recovered email. No manual resolve endpoint in MVP.

Open and observed recovery transitions create outbox entries transactionally; acknowledgment sends no email. Unique `(incidentId,transitionVersion,email,0)` prevents duplicate logical sends. Cooldown 15m applies to future reminders (deferred), never suppresses first opening or real recovery. Provider retries reuse frozen content/recipient and same identity. At most five send attempts, exponential jitter as above, rate ≤1 send/second globally, obey provider Retry-After. Stop automatic attempts by min(outbox created+24h, first send+23h); ambiguous timeout becomes delivery_unknown at deadline. Reconcile provider ID if available; do not issue a new idempotency key to bypass ambiguity. [Resend retains idempotency keys for 24 hours](https://resend.com/changelog/idempotency-keys). Provider acceptance is not recipient delivery; emails can still be duplicated outside that protection and no exactly-once delivery is promised. External watchdog uses an independently configured channel, not this outbox.

Notification states: pending ? sending (leased) ? accepted, pending on retry, failed on permanent/exhausted attempts, or delivery_unknown on unresolved ambiguity/deadline. All terminal states have no automatic send path. Check states: pending ? running ? terminal; expired running leases may be reclaimed only while the slot is fresh, otherwise terminal missed. A probe operation cannot hold an incident transaction open. Alert evaluation evidence is stored in bounded state/current snapshots; timeline records transitions or quality changes only.

## Admin session contract

Single local bootstrap account, no default credential/signup/reset HTTP. Password 12–72 UTF-8 bytes, bcrypt cost measured for 100–250ms, one concurrent password hash/API; login cap 5 attempts/account/15m and 20/IP/15m with generic response. Offline local reset revokes all sessions. JWT 10m, pinned algorithm/issuer/audience, sub/admin and sid/session claims, key ID rotation; token held in memory. Every privileged request checks current admin/session state in MongoDB; unavailable MongoDB fails closed. Max five active sessions, revoke oldest on new login.

Refresh opaque token includes public session ID + ≥32 random bytes; only digest stored. Cookie `__Secure-monitor_refresh`, HttpOnly, Secure, host-only (no Domain), Path `/api/v1/auth`, SameSite=Strict, lifetime bounded by seven-day inactivity and 30-day absolute expiry. Same-site custom HTTPS domains such as console.monitor.example.com and api.monitor.example.com are prerequisite, or approve a same-origin proxy design. Unrelated vercel.app/API domains cannot use this Strict-cookie design.

Session-bound random CSRF token stored hashed; sent on login and `GET /auth/csrf`, returned in `X-CSRF-Token` for cookie mutations. CSRF bootstrap requires exact trusted Origin, valid current refresh cookie, credentials CORS, no-store, rate cap, and exposes no access token; reads from origins outside the exact frontend allowlist are denied. Rotation preserves CSRF token for session lifetime to support cross-tab serialization; token is base64url HMAC-SHA256 of sessionId and a per-session random csrfSalt using a server-only key identified by csrfKeyId. Bootstrap recomputes the same token; database stores salt/key ID/digest, not token. Retain that server key through session absolute expiry during key rotation. Log neither. Refresh atomically consumes current digest and appends it to usedDigests; known used-token replay revokes family; unknown token fails generically. No grace; tabs coordinate a single refresh using a same-origin browser lock and share ephemeral token state, never localStorage credentials. Lost refresh response or unsupported cross-tab locking requires re-login. Absolute expiry and idle expiry checked synchronously, not via TTL.

Exact origin checks on login/bootstrap/refresh/logout and socket upgrades; JSON-only mutations plus CSRF on cookie auth. JWT APIs require Authorization, not ambient cookie auth. Credentials CORS only for fixed frontend origin; previews denied. Logout/revoke/reset disconnect sockets and revoke DB sessions. API key rotation: 90-day default expiry, two active/group, new independent secret shown once, maximum old overlap 24h, immediate emergency revoke; secrets installed in applications only during a later separately scoped rollout. Ingestion reads key/current enabled scope each batch. Exclude Authorization/Cookie/body dumps from all logs, errors, audit and email.

## Socket.IO contract

Namespace `/admin`, transport on API origin; handshake `{accessToken}` in auth object, never query URL. Same JWT/session/origin checks as HTTP. Server assigns `admin` and scoped project/environment rooms; client may not join arbitrary rooms or send telemetry. Max five concurrent sockets/admin, inbound event ≤4KiB and 10/min; only protocol/application ping control, no domain writes. Revalidate sessions every 30s and at sensitive push, close immediately at JWT expiry; Mongo unavailable closes connections. Revocation broadcasts best effort plus periodic check bound; REST revocation is immediate, socket fallback disconnect ≤30s. Minimal invalidations contain no sensitive detail during that bound.

Event names `metrics.updated|incident.changed|check.updated|platform.status`. Envelope: `{version:1,eventId:UUID,projectId?,environmentId?,entityId,revision:integer,occurredAt:UTC}`. Project/environment required except platform.status. Example `{version:1,eventId:"88888888-8888-4888-8888-888888888888",projectId:"000000000000000000000001",environmentId:"000000000000000000000002",entityId:"...",revision:3,occurredAt:"2026-11-21T06:00:00.000Z"}`. After commit only, ≤1 metrics invalidation/scope/second, volatile/bounded send; disconnect slow consumers rather than accumulate messages. Redis pub/sub and sockets may lose messages; REST snapshot on reconnect/focus and 30s polling are mandatory. Clients discard old entity revisions; no persistent replay log. [Socket.IO delivery guarantees](https://socket.io/docs/v4/delivery-guarantees/).

## Module and error conventions

Preserve Model → Service → Controller → Route construction and runtime reverse call direction. `<feature>.validation` owns Zod, `.interface` owns types; feature services own authorization/state/transactions. Models stay private to owning feature. Cross-feature coordinator passes one database session through exported services. Workers/jobs/controllers are adapters only. `platform` owns shared lease/wake/diagnostic primitives, never feature business decisions. Feature map in backend-modules remains authoritative; route registry belongs to environments. Infrastructure owns Mongo/Redis/HTTP/Resend adapters. Frontend stays JavaScript.

Classify operational failures as retryable_dependency, admission, validation, auth, conflict or terminal_work. Unknown defects log safe error class/request/work ID, trigger bounded process shutdown where state may be corrupt, and supervisor restart. Do not retry poison input or continue after uncaught exceptions. No body dumps, raw provider errors, SQL/Mongo diagnostics or target content in queue failures. Pub/sub failure never rolls back a committed workflow. Graceful shutdown stops claims/intake, drains ≤30s, rolls back/abandons unfinished work and closes resources; leases permit recovery.

## Trade-offs, confirmed decisions and open risks

Confirmed here: original stack and feature monolith; three separate processes; durable finite inbox/outbox; MongoDB replica-set requirement; fixed wake-up jobs; at-least-once work with transactional idempotence; metadata-only telemetry; approximate 25-bin MVP percentiles; independent probes; strict admin refresh rotation; REST authority. Stronger durability costs writes/transaction contention; bounded failure behavior intentionally permits visible loss after budgets/deadlines.

Provisional: every numeric rate/concurrency/retention/alert threshold, capacity and RPO/RTO target; same-site domain names are examples. Two-day raw visibility and seven-day minutes fit a smaller pilot than Step 1, but even these can exceed free storage. Coarse histogram intervals can delay/indeterminate p95 alerts; active probes supply faster signals. Fixed wake polling caps throughput and adds up to five seconds of dispatch latency; it removes custom permit and enqueue-reconciliation machinery. Strict refresh reuse detection may log out legitimate racing tabs/lost responses; this is accepted initial behavior, not an untested grace protocol.

Open before rollout: actual peak/mean RPS and BSON/index sizes; VM/provider/region/RAM and per-process supervisor limits; MongoDB provider/topology/version/transaction/pool/backup quotas; privacy permission for managed DB; same-site domain and VPN policy; approved health targets and public reachability; Express/Node compatibility and SDK route extraction; recipient/domain verification and provider quotas; off-host backup location/keys; external watchdog channel; optional MFA. Pin supported Node LTS, MongoDB replica-set version and compatible Mongoose/BullMQ/Redis package versions during foundation, based on reviewed support matrices; this document does not assert versions without that selection. No free hosting SLA or always-on capacity is assumed.

Managed DB reduces operator patch/failover work only to the extent purchased plan provides it. Verify transaction limits, storage/index/oplog, connections (25 initial pool ceiling across processes), egress, suspension and restore capability; do not assume backups on a free plan. Self-managed single-node replica set is transaction-compatible but host/disk loss requires restore; three nodes on the same VM do not isolate that failure. Proper redundant replica set spans failure domains and costs resources. Both require verified encrypted off-host backup/restore, least-privilege TLS/network access, capacity alerts and acceptance of actual failure/RPO behavior. Daily backups imply up to 24h catastrophic loss; proposed restore ≤4h must be tested. Replica redundancy is not a backup.
